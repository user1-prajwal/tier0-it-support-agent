# 0001: Phase 1 decisions (ingestion and dense retrieval)

Date: 2026-11-23. Status: accepted.

## Decisions

| Decision | Why | Rejected |
| --- | --- | --- |
| Schema as plain SQL migrations, no ORM models | The security-critical queries stay explicit and readable aloud | SQLAlchemy models with autogenerate |
| `groups` now. `users`, `user_groups` and `documents.created_by` in Phase 2 | `document_acl` needs `groups`. Users have no consumer yet | Creating every table up front |
| Bigint identity ids. `classification` is a checked label. `document_acl` is the authority | Access can change per document without relabelling it. A typo in a classification is refused by the database | UUIDs, deriving access from the label at query time |
| One active version per source (partial unique index). A changed file retires the old version in the same transaction | The database enforces versioning. Search never serves a replaced document | Deleting old versions, enforcing it only in Python |
| Chunker: pure function, never crosses a heading, overlap only inside a section, code fences tracked | A chunk that mixes topics embeds as a blur and cites the wrong place | LangChain text splitters |
| Local embedder FastEmbed `bge-small-en-v1.5`, vectors normalised, `embedding_model` stored per chunk, ingestion refuses to mix models | Free, deterministic, nothing leaves the machine. Mixed-model vectors give silent nonsense | An embedding API, automatic re-embedding |
| Query prefix is an explicit parameter, default empty | FastEmbed's `query_embed` adds no prefix for this model (checked on the real model). The prefix showed no benefit on the dev set | Assuming a library default |
| Ingestion: TOML front matter, unknown keys rejected, ACL from a classification map checked against a hand-written list, one transaction per file | Standard library only. A typo cannot silently drop a field. A document cannot exist without its ACL | PyYAML (not on the allow-list) |
| Dense search: permission filter and ranking in one SQL query, `EXISTS` on the ACL, active versions only, no groups means no results | Restricted chunks never become candidates | Filtering after ranking |
| Exact cosine scan, no vector index | Perfect recall at this size. Approximate indexes with filters can return fewer rows | HNSW now |
| Evaluation: gold is (document, heading path). Split by hash of the question id. Only dev is runnable. Every run records the commit and a dirty-tree flag. Unreachable gold is rejected | Labels survive re-chunking. The split cannot move. The test split stays unspent. No silent zeros | Chunk-id labels, a shuffled split, RAG evaluation frameworks |

## Deviations from the brief

- Front matter is TOML and eval questions are JSONL, to avoid a YAML dependency. There is no `owner_group` field, because the schema has nowhere to store it.
- The `pgvector` Python package and `db/models.py` are not used. Vectors go in as text literals.
- `eval_runs` was created in Phase 1 and `make eval` does not yet write `docs/EVAL.md`.
- Phase 1 evaluates dense search only. The chunk-size comparison is deferred to Phase 2, because it needs re-ingestion per size and a corpus big enough to show a difference.
- Eval users are a constant mapping from the seeded emails to groups. Phase 2 replaces it with a database lookup.

Reading: both configurations are saturated, because every dev question has a gold chunk in
the top 5 and the top 5 is about 14% of the 36 stored chunks. Without the prefix exactly two
of 23 questions were not ranked first. With it, the MRR corresponds to three. A difference
of one question is within noise, so the data do not show that the prefix hurts. The empty
prefix stays the default because nothing shows it helps. The dev questions are easy by
construction, and the per-category counts (3 to 12) are too small to compare. This baseline
cannot rank retrieval methods.

## Known limits and open items

- Retrieval metrics are saturated. Harder questions (paraphrase, exact-token, multi-chunk, trap pairs) and more distractor documents are the first Phase 2 task, before the ablation.
- A file deleted from `corpus/` is not retired in the database. PDF and DOCX are not supported. Only `#` headings are recognised. `token_count` is an estimate.
- Re-embedding after a model change is not built. Ingestion refuses and says so.
- The test split has not been run, by design.
- Recall@k counts a multi-chunk question as found if any one gold section is in the top k, so it cannot show whether both sections were retrieved. A stricter all-sections measure for multi_chunk questions is a Phase 2 candidate.
