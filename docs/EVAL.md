# Retrieval evaluation

Generated by `make ablation` from `eval_runs` row 12, measured at commit `e3dd83b0f03343d24dd323e0cac048e281e596dd` on the dev split. Do not edit by hand: re-run the command instead.

## Setup

- Corpus: 20 synthetic documents, 110 chunks.
- Questions: 60 labelled in total. This run scored the 45 answerable questions in the dev split. The test split was not run.
- Models: embedding `BAAI/bge-small-en-v1.5`, reranker `Xenova/ms-marco-MiniLM-L-6-v2`. Query prefix: `none`.
- Fusion: RRF with k = 60. The top 20 fused chunks go to the reranker. Metrics use the top 10. The service keeps 5.
- Each search arm returns up to 30 chunks and the askers may read 65 to 98 chunks, so an arm can miss a relevant chunk.

## Limits of this evaluation

- A small synthetic corpus and 60 questions labelled by the author. No real users.
- 30 of the 60 questions are marked `llm_drafted`: first drafted by an LLM, then reviewed and edited by the author.
- The corpus documents were first drafted with an LLM and then edited by the author.
- Gold labels are sections (document plus heading path). A hit means some chunk of the gold section was retrieved. 9 of the 39 gold sections span more than one chunk; for those, a hit may not be the chunk that holds the answer.
- Several questions share a gold section, so the questions are not independent and the effective n is smaller than listed. The sign-test p-values ignore this and are optimistic.
- Only the dev split was run. The test split is run once, at the end of the project.
- Latency is the median over 45 questions on one machine (CPU only). It includes embedding the question and the database round trips, and excludes one warm-up call. It describes this laptop and is not a benchmark.
- Group memberships were read once per run. An offline evaluation changes none. The running service reads them on every request.
