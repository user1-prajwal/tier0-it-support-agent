# Software requests

## Submit a software request

Employees who need software for an approved work task should submit a request through the standard IT service portal. Include the application name, business purpose, device or team that needs it, and the approximate number of users. Explain which work activity cannot be completed with the software already provided. A clear business reason helps the review team assess the request without repeated follow-up.

For example, a design team may request the fictional product `DesignForge Studio` to prepare interface mockups and export review images. The request should explain the project need, required features, expected users, and whether the work involves confidential information. Naming a product does not mean it is approved for use. Do not download an installer from an unverified website while waiting for the decision.

If the request is for a browser extension, command-line utility, developer library, or cloud service, identify the publisher and official product page. Explain what information the tool will access, whether it stores files externally, and whether it requires administrator privileges. Do not include passwords, API keys, access tokens, or customer information in the request.

## Review and approval

IT reviews compatibility with managed devices, licensing, support requirements, and security risks. Some requests may also require approval from the budget owner, data owner, or security team. The review team may ask for a trial plan, a list of required features, or an alternative that is already supported.

The requester should not treat silence as approval. Do not install software using personal administrator credentials, disable endpoint protection, or bypass application controls. If a time-limited trial is necessary, request an approved evaluation environment and state the trial end date. The requester is responsible for confirming that the proposed use complies with the product's license and the organization's data-handling requirements.

The review outcome should be recorded in the service request. Possible outcomes include approved, approved with conditions, more information required, or declined. If the request is declined, the response should explain the relevant constraint and, where possible, identify an approved alternative.

## Installation and ongoing ownership

After approval, installation should be completed through the managed software catalogue or by authorized IT support. Confirm that the installed version matches the approved request and that the application receives updates through a supported channel. The requester should test the required workflow and report any installation or compatibility problem through the original ticket.

The business owner should review whether the software is still needed when the project ends or the team changes. Notify IT if the number of users changes, the product begins processing a different type of data, or the vendor changes its storage or access model. Unused licenses should be returned according to the normal license-management process.
